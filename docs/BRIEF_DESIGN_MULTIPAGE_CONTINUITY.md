# BRIEF_DESIGN_* 다중 페이지 섹션 연속성 문제 — 분석 및 해결 방안

**작성일:** 2026-06-18
**상태:** 보류 (다음 세션 작업 예정)
**관련 케이스:** 영등포구 통합 신청사 국제설계공모 지침서 PDF (p.45~46 직무공간 섹션)
**관련 파일:** `{db_path}/_briefs/20260618_084715_public_*.json`

---

## 문제점 분석 및 해결 방안

### 근본 원인 (Root Cause)

`extract_pdf()`는 BRIEF_DESIGN_* 페이지를 **페이지 단위로 독립 추출**합니다. `_extract_page_sync()`가 각 페이지의 이미지 1장만 LLM에 던지므로:

**페이지 46의 LLM은 다음을 모릅니다:**
- 페이지 45 끝에서 시작된 "직무공간 (부서 사무실)" 섹션이 이어지고 있다는 사실
- 페이지 46 상단의 "- 비품창고", "- 기타 부서별 요청사항"이 페이지 45의 **자식 항목**이라는 사실
- 페이지 46 중간의 "통합 민원실"부터가 **새 섹션**이라는 사실

페이지 46 단독으로 보면 LLM 입장에서는:
- 상단 fragments (① 6명 이용 가능한 ..., 비품창고, 기타 부서별 요청사항) → 부모 헤더가 안 보이므로 임의의 가공 헤더 ("외부시설 계획지침") 를 만들어 붙임
- "통합 민원실", "회의 및 행사공간" → 명확한 헤더로 보이지만 같은 가공 헤더 아래로 평탄화됨

---

### 원본 PDF의 시각적 계층 vs LLM 추출 결과

**원본 PDF (페이지 45~46):**
```
직무공간 (부서 사무실)         ← 페이지 45 시작 (부모 헤더)
  - 상단 [세부시설 면적표]...
  ... 페이지 45 끝 ...
  ... 페이지 46 시작 ...
  - 비품창고                   ← dash, 자식 (직무공간 내부)
    ① 각 부서별 사무실 내...
  - 기타 부서별 요청사항       ← dash, 자식 (직무공간 내부)
    ① 감사담당관 ...
    ⑧ 주택과: 사무실 내 임대사업...
• 통합 민원실                  ← bullet, 형제 (새 섹션)
  - 접근성이 좋은 저층부...
• 회의 및 행사공간             ← bullet, 형제 (새 섹션)
  - 공간과 인원수용 규모...
```

**LLM이 추출한 결과 (페이지 46 `design_guidelines_grouped`):**
- 5개 항목 모두 같은 평면(top-level)에 놓임
- `section_path`가 모두 가공의 `"외부시설 계획지침 > X"` 형식
- 면대실/비품창고/기타 부서별 요청사항 (원래 직무공간의 자식) ≡ 통합 민원실/회의 및 행사공간 (원래 형제) — **구조상 구별 불가능**

### 검증된 사실 (JSON 분석)

페이지 46 데이터는 **사라지지 않았고 JSON에 다 있음:**
1. `space_scope: "면대실"` — `section_path: "외부시설 계획지침 > 면대실"`
2. `space_scope: "비품창고"` — `section_path: "외부시설 계획지침 > 비품창고"`
3. `space_scope: "기타 부서별 요청사항"` — `section_path: "외부시설 계획지침 > 기타 부서별 요청사항"`
4. `space_scope: "통합 민원실"` — `section_path: "외부시설 계획지침 > 통합 민원실"`
5. `space_scope: "회의 및 행사공간"` — `section_path: "외부시설 계획지침 > 회의 및 행사공간"`

→ 엑셀 시트 3에 안 나타나는 이유는 **별개의 라우팅 문제** (facility_scope 처리, 시트 분기 등). 별도 디버깅 필요.

## 해결 방안 3가지

### A안: BRIEF_DESIGN_* 연속 페이지 스태킹 (권장)

이미 BRIEF_EVALUATION / BRIEF_PROGRAM에서 검증된 패턴을 그대로 적용:

- `extract_pdf()` 진입 시 연속된 BRIEF_DESIGN_GUIDE / BRIEF_DESIGN_MASSING / BRIEF_DESIGN_FACADE / BRIEF_DESIGN_SUSTAIN / BRIEF_DESIGN_SPECIAL 페이지를 N장씩 청크(3~4페이지) 단위로 `_stack_images_vertically()` → JPEG 한 장으로 합쳐 LLM에 1회 전달
- 결과의 `design_guidelines_grouped` 항목을 `extend()`로 머지
- 청크 실패 시 페이지별 폴백 (기존 `precomputed_program = None` 패턴 재활용)
- 각 항목에 `source_page` 필드 명시 요청 (LLM 프롬프트 추가)

**장점:**
- LLM이 시각적 들여쓰기/번호체계로 부모-자식 관계 한눈에 파악
- 기존 코드 패턴 재활용 (`_stack_images_vertically`, `_STACK_MAX_DIM=7500`, 폴백 로직 모두 있음)
- 토큰 절감 효과도 있음 (반복적 시스템 프롬프트 1회로 압축)

**단점:**
- BRIEF_PROGRAM(표) 대비 텍스트 밀도가 높아 OCR 한계로 작은 글자가 깨질 수 있음 → DPI 유지 + 청크 크기 보수적으로(3~4페이지)
- 청크 경계가 섹션 한가운데를 자르면 동일 문제 재발 → 청크 분할 시 "다음 페이지가 헤더로 시작하는지" 휴리스틱 검사 후 청크 경계 조정 (선택적 강화)

**비용:** 35페이지 PDF 기준 단독 호출 → 청크 호출로 입력 토큰 약 30% 감소. 출력 토큰은 거의 동일.

---

### B안: 이전 페이지 마지막 섹션 컨텍스트 주입

- `_extract_page_sync()`를 페이지별 순차 실행으로 바꾸고, 직전 페이지의 마지막 `section_path` / `space_scope`를 텍스트로 프롬프트에 추가
- "이 페이지 상단에 새로운 굵은 제목(◯, •, 큰 글자 ■ 등)이 보이지 않으면 직전 페이지의 마지막 섹션 `직무공간 (부서 사무실)`의 연속으로 처리하세요"

**장점:**
- 페이지 단위 처리 구조 유지 (기존 코드 변경 최소)
- 청크 OCR 품질 저하 걱정 없음

**단점:**
- **순차 실행 강제** → 현재 `asyncio.gather` 병렬 처리 대비 추출 시간 N배 (35페이지 PDF면 사용 경험 악화)
- 여전히 LLM judgment에 의존 — "새 제목" 판단이 틀리면 다음 페이지 전체가 직전 섹션으로 흡수됨
- 페이지 47, 48의 별개 섹션 분류 정확도가 떨어질 위험

---

### C안: 후처리 머지 (사용자 제안)

> "페이지 N의 마지막 섹션과 페이지 N+1의 다음 새 섹션 사이에 끼인 내용은 자동으로 페이지 N의 섹션 소속으로 본다"

**최종 평가: 이번 케이스에서는 작동 안 함.**

이유:
- 후처리 단계에서는 `면대실`, `비품창고`, `기타 부서별 요청사항`, `통합 민원실`, `회의 및 행사공간` — **모두 똑같이 생긴 top-level 엔트리**
- 시각적 단서(•=새 섹션, -=자식)는 LLM이 JSON으로 변환하면서 사라짐
- `section_path`가 다 똑같이 `"외부시설 계획지침 > X"` 형식 — "어디서 멈춰야 할지" 알 길이 없음
- 알고리즘이 "통합 민원실은 새 섹션이고 면대실은 자식이다"를 구분할 방법이 **JSON만 봐서는 없습니다**

부분적 활용은 가능 — 페이지 N+1의 첫 항목이 명백히 fragment(① 같은 자식 번호 prefix로 시작, 부모 헤더 없음)일 때만 머지. 하지만 완전한 해결책은 아님.

---

## 권장 조합

1. **A안 (페이지 스태킹)** 을 메인으로 채택 → 추출 단계에서 계층 보존
2. **C안 (후처리 머지)** 는 안전망으로 부적합 — 사례 구분이 안 됨
3. 별도로 **페이지 46 데이터가 엑셀 시트 3에 안 나타나는 라우팅 문제** 디버깅 필요 (이건 다른 문제, JSON에는 데이터 존재)

## 구현 시 영향 범위

**수정 필요 파일:**
- `backend/services/data_extractor.py`
  - `extract_pdf()` 진입부: BRIEF_DESIGN_* 페이지 그룹핑 로직 추가
  - `_DESIGN_STACK_CHUNK = 3` (또는 4) 상수 추가
  - BRIEF_EVALUATION / BRIEF_PROGRAM 스태킹 코드 패턴 재사용
  - 청크별 LLM 호출 + 결과 머지 로직
  - 스태킹 실패 시 페이지별 폴백 분기

**기존 재사용 가능:**
- `_stack_images_vertically()` — JPEG 출력, `_STACK_MAX_DIM=7500` 검증됨
- `_image_block()` — JPEG 마법 바이트 자동 감지
- 폴백 패턴 — `precomputed_eval = None` / `precomputed_program = None`과 동일

**프롬프트 수정:**
- BRIEF_DESIGN_* 스태킹 프롬프트에 "각 항목의 `source_page` 필드 명시" 룰 추가
- 스태킹 시 토큰 한도 (`max_out` ≥ 8000) 확보

**테스트 케이스 (영등포 PDF):**
- 페이지 45+46 스태킹 → "직무공간 (부서 사무실)" 아래 면대실/비품창고/기타 부서별 요청사항이 자식으로 들어가는지 확인
- "통합 민원실", "회의 및 행사공간"이 별도 top-level로 추출되는지 확인
- 청크 경계 (예: 45+46+47 vs 45+46) 비교 — 통합 민원실이 청크 끝에 잘릴 때 처리
