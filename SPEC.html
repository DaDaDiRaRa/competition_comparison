설계공모 경쟁분석 시스템

건축 설계 공모 제안서 PDF를 AI로 추출·분류·비교·진단하는 풀스택 내부 도구의 기술 명세서

작성 기준일 2026-06-29
분석 방법 소스 코드 직접 분석 (7개 병렬 에이전트) + CLAUDE.md
불확실 사항 추정 표시

1목적 및 배경

설계공모 경쟁분석 시스템(Competition Analyzer)은 건축 설계 공모전에서 제출된 제안서 PDF와 공모 지침서(PDF/DOCX/HWP/HWPX)를 자동으로 추출·분류·비교·진단하는 풀스택 웹 애플리케이션입니다. 핵심 목적은 대형 건축사사무소가 다수의 공모 제안서를 체계적으로 분석하고, 과거 당선/낙선 패턴을 축적하여 신규 공모 진단 및 수주 전략 수립에 활용하는 것입니다.

기존의 수작업 비교 방식을 대체하기 위해 Claude AI(Sonnet 4.6 / Opus 4.8)를 LLM 엔진으로 활용하며, 추출된 정량 데이터와 AI 분석 결과를 HTML 리포트로 자동 생성합니다. 평가 결과는 숫자 점수가 아닌 5단계 등급(A/B/C/D/E) 문자열로 표현하여 임원 검토 시 정밀도 논쟁을 최소화합니다.

모든 데이터는 관계형 DB 없이 JSON 파일 시스템으로 저장되며, 운영 환경에서는 GCS 버킷을 GCSFUSE로 마운트하여 사용합니다. main 브랜치 push 시 GitHub Actions를 통해 Cloud Run (gen2)에 자동 배포됩니다.

2.2 배포 환경

  • 운영: Google Cloud Run (gen2), 컨테이너 이미지 빌드 후 배포
  • 스토리지: GCS 버킷 gs://kunwon-competition-db (GCSFUSE 마운트, /data 경로)
  • CI/CD: GitHub Actions (.github/workflows/deploy.yml), main push 시 자동 트리거
  • 로컬 개발: 백엔드 uvicorn main:app --reload --port 8000, 프론트 npm run dev (Vite, port 5173, /api/* 프록시)
  • 패키지 동기화 필수: requirements.txt (로컬) + requirements-server.txt (Docker) — 양쪽 항상 동기화
  • Cloud Run 업로드 한도: 32MB 제한 우회를 위해 청크 업로드 라우터 (/api/upload) 사용
  • CORS: allow_origins=['*'], allow_credentials=False — 전 오리진 허용 (의도적, per-browser API 키 모델)

3핵심 파이프라인

3.1 제안서 축적 (Accumulate)

엔드포인트: POST /api/accumulate/add-submission (SSE 스트리밍)

1
업로드: 25MB 미만은 FormData 직접 전송, 이상은 청크 업로드(/api/upload)로 file_ref 취득.
2
분류(classify): classify_all_pages_brief()가 PDF 페이지를 배치 처리(BATCH_SIZE=5). DPI 72, claude-sonnet-4-6, max_tokens=3000, temperature=0.
3
추출(extract): 3-tier 로직 적용 (§5.2). 제안서 결과에 _quantitative 자동 집계 + quant_validator로 _quantitative_flags 부착.
4
저장: _atomic_write() (JSON), _sync_write() (HTML). 개별 제출물 리포트 즉시 생성.
5
SSE 이벤트: stage / progress / done / error. 모든 이벤트에 _timestamp (epoch ms) 필수.
비교분석은 분리된 별도 호출
POST /api/accumulate/projects/{ft}/{cid}/rerun-compare를 별도 호출해야 합니다. rerender-report는 LLM 없이 HTML만 재생성합니다.

3.2 비교분석 (Compare) — 2-pass Blind-Reveal

엔드포인트: POST /api/accumulate/projects/{ft}/{cid}/rerun-compare

Pass 1
블라인드 채점
  • 제출물을 A안/B안/...으로 익명화, 결과 라벨 제거
  • 정적 프롬프트 + 동적 데이터 각각 cache_control: ephemeral
  • max_tokens=32000, temperature=0
  • 프롬프트 템플릿: .replace() 사용 (JSON 중괄호 충돌 회피)
Pass 2
리빌 + 사후 분석
  • Pass 1 결과 + 실제 결과 라벨만 재전송
  • 원본 추출 데이터 미재전송 → 토큰 ~80% 절감
  • max_tokens=4096 (단문 출력)
  • Gap Analysis: 결정론 Python 로직

Gap Analysis 결정론 로직 (_compute_gap_analysis())

  • blind_top1: 블라인드 1위 제출물
  • actual_winners: result가 win 또는 contracted인 제출물
  • alignment 산출: 상위 절반 = ceil((n+1)/2) 항목. top1 일치 AND 당선작 90%↑ 상위 절반 → "high"; 50%↑ → "partial"; 그 외 → "low"

3.3 제안서 진단 (Diagnose)

엔드포인트: POST /api/diagnose/run (전체 패턴) | POST /api/diagnose/run-vs-projects (선택 제출물)

파이프라인: load_patterns → classify_sub → extract_sub → diagnose → report → complete. LLM 호출 시 2-블록 캐싱(static + dynamic), max_tokens=8192, temperature=0. 완료 시 진단 HTML 자동 생성 (LLM 0). 추정: diagnose SSE 이벤트에는 _timestamp가 없음 (brief SSE와 불일치).

3.4 지침서 분석 (Brief)

엔드포인트: POST /api/brief/analyze (SSE). 지원 포맷: PDF (≤200MB), DOCX/HWP/HWPX (각 ≤50MB).

파일 검증 (_validate_brief_file())

  • PDF: magic byte b'%PDF'
  • DOCX/HWPX: b'PK\x03\x04' (ZIP 포맷)
  • HWP: b'\xd0\xcf\x11\xe0' (OLE2 포맷)

파이프라인 순서

classify_brief → extract_brief → brief_reqs → validate → (옵션) insight → (옵션) site_analysis → save → complete

저장

_atomic_write(json) → _sync_write(md) → _sync_write(html) → _sync_write_bytes(xlsx)

저장 경로: {db_path}/_briefs/{YYYYMMDD_HHMMSS}_{facility_type}_{slug}.{json|md|html|xlsx} (최대 120자)

3.4.1 AI 종합 해설 (brief_advisor)

POST /api/brief/{brief_id}/interpret 또는 /analyze의 include_insight=True(기본값)로 실행.

역할: "해설가" — 사실 triage만
지침서가 무엇을 요구·강조·배점하는지 종합. 당락 예측·전략 처방·외부 지식 주입 금지.
  • 결정론 백본 compute_scoring_focus(): LLM 0. 배점이 가장 많은 페이지에서 카테고리별 points·weight_pct·rank 산출. LLM 출력의 scoring_focus는 이 값으로 항상 덮어씀 (환각 차단).
  • LLM 호출: claude-opus-4-8, max_tokens=16000, temperature=0 (Opus는 자동 생략).
  • 가드 4개: 근거 한정, 인용 필수(페이지 추측 금지), 예측 금지, 중립 탐지만.
  • 산출물: _insight → _brief.json 내 임베드. 체크리스트 HTML/MD/xlsx 3종 모두 렌더링.

3.4.2 수주 제안서 (brief_proposal)

POST /api/brief/{brief_id}/propose 호출.

역할: "전략가" — 처방형 전략 (brief_advisor와 별개 산출물)
앞을 보는 처방 — 수주 핵심 테마·설계 접근 방향·착수 우선순위·리스크·체크리스트.
  • 결정론 백본 재사용: brief_advisor._build_advisor_payload() + compute_scoring_focus() 그대로 import (드리프트 차단).
  • 패턴 주입: _pattern_signals(facility_type)로 동일 시설유형 당선/낙선 경향 → payload["pattern_context"].
  • 고정 설계: win_themes 1~2개 압축, design_directions 상호 배타 컨셉 5안 고정, risks 2층(명시 실격 + 반복 강조 추론).
  • AI 해석 확장층 (Phase 2): program_directions / massing_strategy / phasing 신규 필드 ({claim, basis} 구조).
  • 수치 검산: proposal_number_check.check_proposal_numbers() (LLM 0) → _number_flags 부착 (숫자 수정 0, 비치명).
  • 산출물: _proposal → _brief.json 임베드 + {brief_id}_proposal.html 별도.

3.4.3 대지·맥락 분석 (vworld_analyzer)

POST /api/brief/{brief_id}/site-analyze 또는 지침서 분석 완료 후 자동 실행 (feasibility_export.sites[0].address 비null 시).

단계내용
지오코딩GET /req/address (ROAD → PARCEL 순서), EPSG:4326 반환
위성 이미지WMTS 타일, zoom=16, 3×3 그리드 (~1.8km 범위)
지적도 오버레이WMS GetMap, layers=lp_pa_cbnd_bonbun,lp_pa_cbnd_bubun, 중앙 900m/768px 요청 (~1.2m/px) → 광역 위성 위 합성
병렬 취득asyncio.gather로 WMTS + WMS 동시 요청
Vision 분석claude-sonnet-4-6, max_tokens=1500, temperature=0
폴백alpha=0 / 오프셋 이탈 / PIL 오류 → 위성 단독 이미지 (비치명)
⚠️ 스케일 임계는 m/px (절대 span 아님)
좁은 영역을 고해상으로 요청해야 렌더됨. 구 레이어명 lp_pa_cn_A는 오타(LayerNotDefined 발생).

3.5 교차 비교 (Cross-Compare)

엔드포인트: POST /api/accumulate/cross-compare (SSE). 여러 프로젝트에서 선택한 제출물들을 교차 비교합니다. 결과는 _cross_reports/*.html로 저장됩니다.

3.6 아카이브 검색 (Archive)

엔드포인트: GET /api/archive/list, POST /api/archive/search

  • FTS5 인덱스: 앱 시작 시 1회 구축 (in-memory SQLite). rerun-compare 후 rebuild_index().
  • 토크나이저: trigram 시도 → OperationalError 시 unicode61 폴백.
  • 검색 흐름: 2자 이하 → 전체 리스트. 3자 이상 → Claude (max_tokens=300)가 2-5개 FTS 키워드 추출 → FTS5 OR 쿼리. LLM 실패 시 직접 키워드 검색 폴백.

8운영 규칙 및 제약

8.1 파일 저장 규칙 (GCSFUSE 대응)

⚠️ GCSFUSE fsync 필수
운영 스토리지는 GCSFUSE이므로 Python 일반 파일 쓰기는 GCS 플러시를 보장하지 않습니다. 모든 신규 파일 저장 함수는 반드시 아래 두 원시 함수 중 하나를 사용해야 합니다.
함수용도특성
_atomic_write(path, data)JSON 저장.tmp 파일 → fsync → rename. 크래시 내성(partial write 없음)
_sync_write(path, text)HTML/MD 저장직접 쓰기 + fsync. 추정: rename 없어 크래시 시 부분 파일 가능성
_sync_write_bytes(path, bytes)xlsx 저장동일 패턴

8.2 API 키·보안

  • API 키 전달: HTTP 헤더 X-Anthropic-Api-Key. 세션 쿠키/토큰 없음.
  • 우선순위: asyncio ContextVar (per-request) → 세션 메모리 → ANTHROPIC_API_KEY 환경변수.
  • 영속화 금지: app_settings.json에 API 키가 있어도 로드 시 자동 제거.
  • 정제 (_sanitize_api_key()): UTF-8 BOM(﻿), zero-width 문자, 선두 -n shell 아티팩트, 양쪽 따옴표 제거. 메모장/PowerShell Set-Content -Encoding utf8 저장 시 BOM이 붙어 httpx UnicodeEncodeError 발생.
  • VWorld API 키: VWORLD_API_KEY 환경변수 전용.
  • 커밋 금지 파일: service.yaml, gcp-sa-key.json, .env, env.yaml.
  • 인증/접근 제어: 현재 로그인 시스템 없음 (의도적 보류). 재개 시 앱 비밀번호 vs Google IAP 검토.
